# Eyes 引擎与 Three.js 的实际接缝

本文分析已签入的恢复源码。Eyes 的实体、星历、资源调度、相机约定属于业务引擎；Three.js 提供数学对象、场景容器、GPU 几何/材质与 WebGL 提交。不能用 Three 的默认场景示例反推 Eyes 的坐标或生命周期。这里的 CPU 集成检查不会证明 GPU 着色器编译、真实浏览器后处理或完整显卡兼容性。

## 入口与版本

`engine/pioneer/public-api.js:202` 使用 `export * as THREE from "../../vendor/three/index.js"`。`vendor/three/index.js:2` 导入 core，文件末尾显式重导出 core API，同时实现 WebGLRenderer。因此组件的 `PioneerPublicApi.THREE.Mesh` 和 `THREE.WebGLRenderer` 来自同一本地供应商边界。`vendor/three/core.js` 的 `REVISION="185"` 才是恢复应用的运行版本。根 `package.json` 的 `three:0.186.1` 服务根项目依赖，不能作为恢复 Eyes 的版本证据。

官方对照锁定 [r185 Object3D](https://github.com/mrdoob/three.js/blob/r185/src/core/Object3D.js)、[r185 InterleavedBufferAttribute](https://github.com/mrdoob/three.js/blob/r185/src/core/InterleavedBufferAttribute.js) 和 [r185 Texture](https://github.com/mrdoob/three.js/blob/r185/src/textures/Texture.js)。Object3D 明确区分局部矩阵更新与世界矩阵传播；交错属性通过 stride/offset 读取同一 backing buffer；Texture.clone/copy 保留 Source 共享。这三项约定都由本文测试直接运行本地类验证。官方当前网页可能已升级，版本判定以签入源码为准。

## 帧与渲染路径

`Engine._loop` 依次推进引擎时间、`Scene.__update`、视口相机变量、`Scene.__updateVisuals`，清空画布，然后逐个 `Viewport.__render`。Engine 构造器建立唯一 WebGLRenderer，启用 scissor 并设置 devicePixelRatio；Scene 构造器建立 Three.Scene。

Viewport 将 DOM 顶部原点换算为 WebGL 底部原点：`rootHeight-offsetTop-offsetHeight`，设置 viewport/scissor/clearColor，再调用相机 prepare/render。同一 Three.Scene 可被多个 Eyes 相机逐次准备和渲染：每次都重写对象相机相对位置、朝向和深度 uniforms。不能把某次对象 position 当成永久世界坐标，也不能假设多个 viewport 独立拥有复制的模型。

`CameraComponent` 构造器 创建 PerspectiveCamera、4x MSAA WebGLRenderTarget 和 EffectComposer：RenderPass → 可选 OutlinePass → 可选 UnrealBloomPass。`CameraComponent.__render` 只把实体朝向赋给 Three 相机，再执行 composer.render；相机位置保持原点。RenderPass 最终调用 renderer.render(scene,camera)，renderer 负责世界矩阵、渲染列表、材质程序、attribute 绑定与 draw 提交。该路径的 vendor 细节见同目录 renderer 分析。

## 坐标、单位与手动矩阵

`Entity-62.__updateCameraVariables:714` 从相机实体开始沿实体父子树加减各级位置，得到以相机为原点、仍保留实体世界轴方向的位移；`__setCameraDependentVariables:610` 缓存此结果。名字 cameraSpacePosition 不能理解为已经乘过相机逆旋转的 view position。`CameraComponent.getNormalSpacePositionFromCameraSpacePosition` 才先逆旋转到相机朝向帧再投影。另一个 `cameraDepth` 参数递归每层加一，是实体树距离/下载优先级，并非沿视轴的几何深度。

`ThreeJsHelper.setPositionToEntity` 将该相机相对位移拷贝给 Three Object3D.position；可选 offset 可先按实体旋转。模型局部顶点和物理半径最终在此相加，保持同一距离单位。应用距离系统把实体距离解释为千米（`DistanceManager._getDistanceParams:493`；光行时使用 `299792.458 km/s`，`:960`）。Three 本身没有千米单位；模型导入缩放、WMTS 米坐标转换仍须按各资源代码查看，不能把所有原始纹理/地理数据数字都称为千米。

Eyes 相机以 **+Y 前向、+Z 向上**。`CameraComponent._updateProjectionMatrix` 的齐次 w 等于相机朝向帧的 y；投影屏幕纵坐标来自 z，x 为横向。这与 Three 默认 -Z 前向不同，Eyes 用自定义 projectionMatrix 与配套 inverse 实现，而非把所有实体坐标交换轴。fieldOfView 初值约 π/3，三角函数接收弧度；合法性条件却写 `<180`，这只是现存宽松边界，不能把其 public FOV 当成角度制。测试以 `(2,10,3)`、90°、aspect=2 得到 NDC `(0.2,0.6,…)`，逆矩阵恢复原点坐标，并验证负 Y 落在可见深度之外。

`ThreeJsHelper.setupObject` 把 matrixAutoUpdate=false、frustumCulled=false、visible=false，并加入场景。setPosition/setScale/setOrientation 只改 TRS；`BaseComponent.__prepareForRenderBase:164` 先让派生类设置相机相关 TRS/uniform，再逐对象显式 updateMatrix。Three 后续仍传播 matrixWorld；禁用的是局部自动 compose，不是所有矩阵运算。CPU 检查证明，未调用 updateMatrix 时局部点 `(1,2,3)` 不受新 position/scale 影响；提交后变为 `(12,24,36)`。

frustumCulled=false 明确关闭 Three 对这些对象的自动几何包围体剔除；源码不能单独证明原作者关闭它的具体原因。Eyes 自己按实体覆盖、可见性和像素大小管理组件，装载阈值 0.5 像素、卸载阈值 0.25 像素（BaseComponent），不能因此说它完全没有裁剪。Viewport 像素映射只接受严格 `-1<z<1`，边界返回 NaN；屏幕方向拾取还有 x/y 范围检查。

## 几何、材质和深度协议

多数曲线实际是 Mesh + ShaderMaterial 扩出的三角形带，并非 THREE.Line。`LineMesh` 用 15 float 交错顶点：当前位置 3、前点 3、后点 3、RGBA 4、带符号宽度 1、dashOffset 1；按 Uint16 索引容量拆块。Trail 用另一套 12 float 布局，不能共用 stride。ThreeJsHelper.createGeometry 的 interleaved=true 初始分配零长度共享 buffer；普通 setVertices 只处理 BufferAttribute，不更新 InterleavedBufferAttribute，调用者必须像 LineMesh/Trail 一样管理 data.array 与 dirty/version。

ShaderMaterial 接收 Three 内建矩阵声明；RawShaderMaterial 则由业务 shader 显式提供声明。Eyes 的 ShaderChunkLogDepth 是自己的深度协议，不等于 renderer 的 logarithmicDepthBuffer 开关，也不是 Object3D.customDepthMaterial。Vertex 保存 gl_Position.w；fragment 将 near→mid 线性压到前半区，mid 以上用 log2 压到后半区，invertDepth 可翻转。BaseComponent 在逐相机 prepare 时填 invertDepth/nearDistance/midDistance。应保持正向距离和同单位，near=mid 会除零。Atmosphere、粒子、标签等 shader 拼接这个 chunk；默认 Three 材质或阴影深度材质不能自动替代。

`cloneMaterial` 先调用 material.clone，再克隆 uniform 的 number/null、数组与可 clone 对象。向量与 Texture 对象会独立，但 Texture 的 Source 保持共享；销毁 ImageBitmap 可影响其它引用。它不是任意 JS 值深拷贝器：boolean/string/plain object 没有 clone；Three 自身 uniform clone 对嵌套数组也有限制。现有 CPU 检查使用实际 ShaderMaterial 验证向量隔离、Texture 对象分离而 Source 同一，以及 destroyTextures=false/true 的 dispose 差异。

## 动态星历与 Three 的边界

`controllers/DynamoController.js` 的记录读取和插值使用 Pioneer.Reader、业务 Vector3/Quaternion 与实体 setPosition/setVelocity/setOrientation。`PosPoint` 按 Float64 样本做位置/速度 Hermite 插值；其它记录各有自己的采样宽度和更新协议。它不调用 Three 的 AnimationMixer、KeyframeTrack 或曲线积分器。Scene 调度控制器使实体状态先于视口相对位置和 GPU 资源更新；Three 得到的是已求值的 TRS/attribute/uniform。`OrbitalParticlesComponent.__update:27–38` 也是业务 OrbitalElements.project 再写实例 offset。轨道动力学与渲染 API 可以分别测试，替换 Three 不会自动替代 Dynamo 插值，更新 Three 更不应重写文件记录格式。

## 资源所有权与已复现问题

ResourceManager 按 URL/type 共享资源，acquire 增计数，release 减计数；最后释放后已完成资源等待 15 秒可复用，未完成任务取消（`managers/ResourceManager:62–76`）。因此 SpheroidLOD、Rings、WMTS/CMTS 先 release 或 releaseAllForEntityItem，再 destroyMaterial(false)；不能同时对共享贴图做直接 dispose。Sprite/Label 还为共享几何与材质模板维护 useCount，并手动从父节点移除实例。

GLBufferAttribute 持有外部创建的 WebGLBuffer；helper 直接 bufferData/bufferSubData，并将 count、type、elementSize 交给 Three。destroyGeometry 中的原生 deleteBuffer 需要 component 才能取得 context。renderer 对已经登记渲染的 geometry.dispose 也有清理路径，所以仅凭缺少 helper deleteBuffer 不能断言所有情况下 GPU 缓冲都泄漏。

本次测试先复现两处接缝缺陷：原 destroyObject 只处理 Mesh，Starfield 的 Points 几何无 dispose 事件；递归销毁及 destroyAllObjectsAndMaterials 未传 component，使从未提交渲染的外部 GLBufferAttribute 无法经 helper 删除。本次已修复 helper：Mesh/Points/Line 均释放几何，递归与批量销毁均传递 component；三条先红后绿的回归断言确认此修复。无须 GPU 即可复现原生 context 调用缺失。Starfield 每次加载创建独立几何；LineMesh 是 Mesh。Sprite/Label 的共享几何走专用卸载逻辑，不经过此修复路径。

另外观察到但本次不擅自修复：CameraComponent.__destroy 未显式 dispose composer/outline/bloom/MSAA target；Spout 自建多个 render target 而未定义对应清理钩子；cloneMaterial 对非 clone 型值不通用；createGLBufferAttribute/updateGLBufferAttribute 仅在旧 ELEMENT_ARRAY_BUFFER_BINDING 为 truthy 时恢复绑定，旧绑定 null 的情形会留下新绑定。它们需要分别确认实际生命周期/GL状态契约，本文不把静态疑点升级为已证实线上故障。
