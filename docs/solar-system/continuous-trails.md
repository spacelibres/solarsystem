# 连续拖尾修正（0.2.39）

## 现象与根因

0.2.38 虽然恢复了卫星位置和历史轨迹，但不能据此视为 Eyes 拖尾效果已经完成。
此次处理用户指出的过长、节点亮斑、放大后折线和随时间跳跃问题。

1. 普通拖尾沿用原始实体颜色，忽略了 `BaseApp.js:345–347` 初始化时调用
   `TrailManager.setColor` 的覆盖。Eyes 的普通拖尾最终是白色、透明度 0.35。
   `TrailComponent.js:233–237` 还叠加了近景和靠近航天器时的淡出，旧版均未完整接入。
2. `lengthCoverages` 中的无穷边界在生成目录中是字符串，旧映射只接受纯数字，
   因此丢失部分任务的长度覆盖。该错误并非所有任务拖尾过长的统一原因；ISS 的
   5573 秒和 Hubble 的 5748.5 秒显式长度本来就来自源端，不能随意整体缩短。
3. `Line2` 的独立线段端帽在相加混合时重叠，造成接点发亮。仅用 shader 修改
   分段线宽和透明度，没有恢复源端连续线带的拓扑。
4. 旧版每隔 `duration / 240` 秒重新采样并替换整条几何；期间只拖动最后一个端点。
   历史采样时间整体移动，加上近景仍以距父天体数千公里的 Float32 坐标绘制，
   会产生可见跳变和坐标量化。

## 改动与依据

- `config/scene-catalog.ts` 保留无穷边界；源时间覆盖使用左闭右开区间。
- `config/eyes-display.ts` 复用 VisibleInterval 的 normal-radius 淡出，并乘以
  `clamp(1000 × 相机距航天器 / 航天器距父天体, 0, 1)`，对应 TrailComponent。
- `render/trail-ribbon.ts` 依据源 `TrailShader.js`、`LineShader.js` 的相邻顶点、
  双侧顶点和连续接缝方法，适配官方 Three.js 的 -Z 相机、对数深度及输出色彩空间。
  相邻线段共享接缝，不绘制重叠圆帽；尾端宽度 0、头端 2 像素，悬停为 2–4。
  闭合行星/月球轨道使用同一连续拓扑，但保持原应用色值、恒定线宽和透明度。
- 抗锯齿使用像素覆盖率，零宽度尾端的覆盖率为零，不用降低整体透明度掩盖接点。
- `domain/rolling-trail.ts` 保留绝对 ET 的历史采样点；首尾每帧按同一时刻的星历
  移动，轨迹头与物理状态同步。可用叶中的采样不触发网络；越过缓存覆盖才重新请求。
  日期跳出覆盖时不把当前位置强接到旧轨迹上。
- 放大时按真实星历细分可见曲线，屏幕中点误差目标为 1/4 CSS 像素；每条曲线最多
  4096 点、细分深度最多 20，不使用任意装饰样条替换物理轨迹。
- 顶点在 CPU Float64 中减去当前观察参考原点后，才写入 GPU Float32 缓冲，
  避免 ISS 等近景在地心大坐标上进行低精度相减。GPU 缓冲复用，只上传使用区间。
- 缓存投影结果；暂停且相机不变时不重复采样和上传。保持既有资源并发及释放规则。
- 恢复源端默认关闭的小型天然卫星图层，分类来自 `EntityCatalog.json` 的
  `Minor Moon`，不猜测名称或大小。新增“小型天然卫星”开关；目录仍可搜索全部
  对象，直接选中的小型卫星及其父参考体不会被这个默认设置隐藏。

## 验证范围

回归测试覆盖连续共享接缝、闭合接缝、固定线宽/拖尾模式切换、色彩输出、近裁剪、
零宽度尾端、局部上传、近景精度、半开长度区间、移动首尾、倒放、日期跳转、
屏幕误差和固定数据边界下不反复重建。

真实 NASA ISS 数据连续运行 240 帧、每帧推进 1 秒（等价于 60 秒/秒、60 FPS），
每帧头端与当前星历状态同步；移动尾端另由回归测试验证；以航天器为原点上传后，GPU 轨迹头误差为 0 km。
该检查验证数据与缓冲更新，不能替代浏览器动态和 GPU 画面验收。
在 ISS 的真实轨迹近景中，另取 148 个可见真实参考点对照细分弧线，测得最大
屏幕距离约 0.00101 CSS 像素，低于该案例的 0.25 像素目标。

这次保留源端完整历史时长，通过正确渐隐呈现可见拖尾，不使用统一长度裁剪。
极端放大仍受 4096 点/20 层预算限制；跨父参考体、旋转参考系、部分源数据的
重复时刻/姿态解析缺口，继续见前版文档，不宣称所有对象、所有日期均已等价。
