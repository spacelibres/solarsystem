# Multi-language display layer

The recovered Eyes application under `eyes/` now ships an adaptive display
language layer. The UI follows the visitor's language when it is supported, and
can be switched at runtime from the settings cluster without leaving the scene.

## Languages

| Code    | Language              | Notes                          |
| ------- | --------------------- | ------------------------------ |
| `en`    | English               | Source catalogue and fallback  |
| `zh-CN` | 简体中文              | Simplified Chinese             |
| `zh-TW` | 繁體中文              | Traditional Chinese (Taiwan)   |
| `ja`    | 日本語                | Japanese                       |
| `ko`    | 한국어                | Korean                         |
| `fr`    | Français              | French                         |
| `de`    | Deutsch               | German                         |
| `es`    | Español               | Spanish                        |
| `pt-BR` | Português (Brasil)    | Brazilian Portuguese           |
| `ru`    | Русский               | Russian                        |

## How the language is chosen

Resolution order, first match wins:

1. `?lang=<code>` in the browser URL **or** in the hash query (`#/earth?lang=ja`).
2. `localStorage["spacelibre.locale"]` (written when the picker is used).
3. `navigator.languages` / `navigator.language`.
4. English.

Regional tags are mapped onto the shipped catalogues (`zh-Hans` → `zh-CN`,
`zh-HK` → `zh-TW`, `pt-PT` → `pt-BR`, `fr-CA` → `fr`, and so on). The active
code is written to `<html lang>` and `data-locale`, so CSS can adapt typography
per language.

The picker is the globe/language button injected at the top of the settings
cluster (bottom-right). Selecting a language stores it, adds `lang=` to the URL
and reloads once so every component, remote resource and date format is created
in the new language. The reload keeps the current route and time query.

## Where the strings live

```
eyes/src/i18n/
  index.js        locale registry and negotiation (pure)
  core.js         translation engine, DOM walker, measurement/title helpers
  install.js      boots the layer before the app graph; runtime patches
  switcher.js     injected language picker
  locales/en.js   English source catalogue (keys are the rendered English text)
  locales/*.js    generated catalogues with identical shape
tools/i18n/translations/<code>.json   translator-owned source for each catalogue
eyes/shell/i18n.css   picker styling, CJK typography, CSS-content overrides
```

`en.js` is the single source of truth. Each other locale is generated from
translator-owned JSON source by `node tools/i18n-apply.mjs <code>`; generated
modules keep the same keys, pattern ids/regexes, entity ids and section shapes,
so a missing translation falls back to English instead of breaking the UI.

The catalogue contains four kinds of display text:

- `messages` — exact English text rendered by templates, components and local
  configuration (`app/config/settings.js`, share/embed options, layer names,
  story catalog titles, surface-map titles, onboarding prose, toasts, hints).
- `patterns` — dynamic sentences with captures (counts, entity titles,
  possessives, loading labels, light-time/scale measurements).
- `entities` / `entityAliases` — localized names for planets, dwarf planets,
  major moons, comets, notable asteroids and famous spacecraft. Entity aliases
  are matched for display and localized names are also added to the search
  index so e.g. `地球` finds Earth.
- `html` — the onboarding overlay blocks, translated as whole HTML so inline
  `<strong>` markup and word order survive translation.

## Translation at the DOM boundary

The recovered NASA component modules are left as recovered. Instead, the layer
translates text where it becomes visible:

1. Before the app graph evaluates, `install.js` configures the active catalogue.
2. `AppUtils.htmlToElement`, `htmlToElements` and `htmlWithParamsToElement` are
   wrapped so template/element HTML is localized before tooltips (tippy) read
   their `data-tippy-content`.
3. A `MutationObserver` translates text nodes and the display attributes
   (`placeholder`, `aria-label`, `title`, `data-tippy-content`, `alt`) added by
   components later, including animated clocks, menus and carousels.
4. `TitleManager.updateTitle` translates the document title.
5. `TimeManager.getDateFormat` supplies locale date/time/parse formats and both
   moment copies receive the locale, so month names and the clock are localized.
   `Number`/`Date.toLocaleString` default to the active locale, so formatted
   distances and dates follow the chosen language.
6. CSS-generated labels (`Previous`, `Next`, `Re-framing follow camera`) read
   localized values from CSS custom properties written at startup.

The result is that every locally-shipped display string can be translated
without touching the recovered executable modules, and the English build is
byte-for-byte behaviourally unchanged (translation short-circuits for `en`).

## Coverage and boundaries

Translated:

- every local UI template and component string, settings/embed options, layer
  and menu categories, search feedback, tooltips and accessibility labels;
- locally shipped catalogs: entity names (major bodies and notable spacecraft),
  categories/subcategories, story catalog titles and the five local story slide
  titles, captions and descriptions;
- onboarding overlay, loading/embed screens, kiosk and tutorial controls;
- clock/date, number formatting and document `<title>`/description.

Not translated by design:

- NASA runtime content fetched from `eyes.nasa.gov` (entity long descriptions,
  event tables, autoplay/featured-event text). NASA serves that content in
  English only; translating it would mean re-authoring external data.
  Surrounding local UI labels are translated.
- Brand names (`spacelibre`, `NASA`, `Eyes on the Solar System` in the welcome
  block), keyboard keys (`A/D`, `SHIFT`, ...), international designations
  (`3I/ATLAS`, `67P/Churyumov-Gerasimenko`, `L1`, `DART`, ...) and minor-moon
  designations that are internationally used in Latin script.
- Interface scripts without a localized name: keyboard shortcuts, unit symbols
  used in protocol-style labels.

Entity coverage is best-effort rather than a strict percentage: language
communities localize different sets of moons, asteroids and missions. The strict
release contract is the interface catalogue (`messages`, `html`, `patterns`);
planet/major-moon names are required, the rest is reviewed per language. The
static audit still prints the exact untouched entity list per locale so a
reviewer can see the deliberate designations.

## Editing translations

1. Edit `tools/i18n/translations/<code>.json` using the same keys as
   `en.js`. (An optional `.tmp-i18n/<code>.*.json` chunk can stage a work-in-
   progress pass; it overrides the checked-in file.)
2. `node tools/i18n-apply.mjs <code>` regenerates
   `eyes/src/i18n/locales/<code>.js`.
3. `node tools/i18n-audit.mjs <code>` reports parity and translation coverage.
4. Rebuild Eyes (`cd eyes && npm run build`, or the watched dev server does it).

Do not hand-edit the generated locale modules; the apply command overwrites the
generated JSON body. `en.js` is hand-maintained.

## Adding another language

1. Add the catalogue to `eyes/src/i18n/locales/<code>.js` with the same shape as
   `en.js` (the apply command can bootstrap it from
   `tools/i18n/translations/<code>.json`).
2. Add the import and code to `LOCALES` in `eyes/src/i18n/index.js`, plus any
   regional aliases in the same file.
3. Add the code/name/intl/moment/date formats to `META` in
   `tools/i18n-apply.mjs`.
4. Translate the catalogue and run the audit.

## Verification

```sh
npm run i18n:check                # tools/i18n-audit.mjs --strict
npm run i18n:browser              # Playwright DOM/screenshot/layout audit
node tools/i18n-audit.mjs         # full parity + coverage table (all locales)
npm test                          # includes tests/eyes-i18n.test.ts
```

`tests/eyes-i18n.test.ts` pins the catalogue shape, capture placeholders, locale
negotiation and the engine's pattern/measurement behaviour. The browser audit
covers the home, object, story, info, settings, menu and distance states for
every locale at desktop and mobile sizes.

## Repository guards

The i18n layer is additive: recovered component modules keep their executable
source and generated catalogs are new files. Two integration points touch
existing boot/shell files:

- `eyes/src/main.js` gains one import (`./i18n/install.js`) so locale
  configuration runs before the application graph. Because `main.js` is a
  frozen-AST boot guard, its entry in
  `tools/lib/preserved-eyes-contracts.json` is updated and the change is listed
  in `docs/eyes-analysis/semantic-progress.json` exceptions; no accepted module
  hash is altered.
- `eyes/src/ui/templates/InfoPanelTemplate.html` annotates the onboarding blocks
  with `data-i18n-html` keys (the template is not part of the semantic pin set),
  and `eyes/shell/index.html` links the new `i18n.css`.

Entity coverage in the static audit is reported for review, not enforced: the
strict release contract covers messages, onboarding HTML and dynamic patterns,
while proper-noun entity names remain a per-language editorial decision.
