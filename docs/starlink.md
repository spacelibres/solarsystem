# Starlink constellation layer

The Explorer's Earth view can display the whole public Starlink constellation as
a live point shell plus a highlighted display orbit for a selected satellite.


## Data source

Starlink publishes one CCSDS OCM ephemeris per satellite:

- `https://api.starlink.com/public-files/ephemerides/MANIFEST.txt` lists the
  current set (11,151 satellites at the 2026-10-19 generation).
- `https://api.starlink.com/public-files/ephemerides/STARLINK-<number>.txt`
  contains 72 hours of position/velocity states in ITRF2000.

Downloading every complete file would be roughly 56 GB. The public server
supports HTTP Range requests, and each OCM starts with its metadata and first
state vector, so [`tools/starlink/build-catalog.mjs`](../tools/starlink/build-catalog.mjs)
fetches only the first 8 KiB of every file. It converts the ITRF position and
the rotating-frame velocity into an inertial state, writes
[`src/data/starlink-orbits.json`](../src/data/starlink-orbits.json), and caches
the raw header windows under `.cache/starlink/` for `--resume` runs.

```bash
npm run starlink:build                 # refresh all 11k satellites (~7 min)
npm run starlink:build -- --limit 50   # smoke test
npm run starlink:build -- --resume     # reuse cached headers
npm run starlink:dates                 # refresh GCAT launch dates
npm run starlink:models                # regenerate the three Gen GLBs
```

The generated catalogue stores `{ n, name, e, p, v }` where `e` is the epoch in
Unix seconds and `p`/`v` are Earth-centred inertial km and km/s. `npm run
starlink:build -- --out ...` writes elsewhere for experiments.

## Runtime display

### Recovered Eyes app

The default Eyes app also loads the same catalogue. Its
[`eyes/src/app/StarlinkLayer.js`](../eyes/src/app/StarlinkLayer.js) creates one
`starlink_constellation` entity parented to Earth and adds Pioneer's
`OrbitalParticlesComponent`. All 11,151 satellites are projected from
`Pioneer.OrbitalElements` into a single instanced particle draw, so no per-satellite
Eyes entity or label is created. The layer appears in the Earth close-up view and
uses the public copy at `public/eyes/data/starlink-orbits.json`; the build tool
writes both that copy and `src/data/starlink-orbits.json`.

### Explorer

- Every valid epoch state is propagated with a two-body Kepler solver in
  [`src/solar/domain/starlink.ts`](../src/solar/domain/starlink.ts).
- [`src/solar/render/starlink-layer.ts`](../src/solar/render/starlink-layer.ts)
  draws all satellites in **one** Points draw call, updates their positions each
  animation frame, and draws a bright selected orbit. 11k translucent orbit
  rings were removed because they painted a blue haze over Earth.
- The layer is anchored to Earth's per-frame position and can be toggled with
  **星链卫星 (11,151)** in the Explorer sidebar.
- Type a public number such as `STARLINK-34567` and press **定位轨道** (or Enter)
  to frame Earth and highlight that satellite's display orbit. Every number in
  the manifest is available without another network request at runtime.

## Dynamo (.dyn) format

Starlink detailed trajectories are exported to NASA Eyes' native dynamo pos
format so they load through the same DynamoController as the rest of the app:

- 
ode tools/starlink/build-dyn.mjs writes three generation samples under
  eyes/src/dyn/starlink/starlink-gen{1,2,3}/def.dyn.
- Each file is dynamo v2: an inline pos block with 385 Hermite samples at
  30-minute spacing over eight days, Earth-centred inertial km and km/s, and ET
  timestamps.
- The Eyes build publishes the files to public/eyes/dyn/starlink/.
- --all --out public/eyes/dyn/starlink can generate a deploy-time pack for
  every catalogue entry; it is intentionally not committed.
- The 11,151-satellite overview remains one point cloud because 11k individual
  dynamo controllers/downloads would be prohibitive. Selected satellites and the
  three generation samples use the shared .dyn format.

## Satellite picker and filters

The Explorer sidebar's **选择卫星** button opens a multi-select picker rather than
requiring a known number:

- search by `STARLINK-34567` or just `34567`;
- multi-select **Gen1 / Gen2 / Gen3** checkboxes;
- filter by **launch year / month / day** (any combination, all optional);
- select individual rows, **全选当前结果**, or clear the draft;
- **应用选中** highlights every selected orbit in one merged line draw and loads
  3D models for the first 12 selections.

Every row shows the public number, generation and launch date. The list is
windowed to 200 rows with **显示更多**; filters are evaluated against all 11,151
satellites, and **全选当前结果** selects the whole filtered set even when only the
first rows are visible.

Launch dates come from Jonathan McDowell's
[GCAT SATCAT](https://planet4589.org/space/gcat/) (CC-BY). The compact map is
generated by
[`tools/starlink/build-launch-dates.mjs`](../tools/starlink/build-launch-dates.mjs)
and merged into the catalogue as `d` (date) and `lt` (launch tag). GCAT's public
snapshot lags a small number of newest launches; those 499 satellites borrow the
nearest numbered neighbour's date and are marked `di: true` (the UI shows
“推算”). The current catalogue has no missing dates.

## Generation model libraries

The project ships three model families under
[`eyes/src/models/starlink/`](../eyes/src/models/starlink/), with a manifest at
[`manifest.json`](../eyes/src/models/starlink/manifest.json):

| Generation | Public number band | Model | Used for |
| --- | --- | --- | --- |
| Gen1 (v1.0 / v1.5) | `< 30000` | `starlink-gen1.glb` | compact bus, one solar wing |
| Gen2 (v2 Mini) | `30000-39999` | `starlink-gen2.glb` | larger bus, two solar wings |
| Gen3 (V3) | `>= 40000` | `starlink-gen3.glb` | Starship-class envelope, two very large wings |

The numbering bands are a display convention exposed as the `g` field in
`starlink-orbits.json`; they are not an official SpaceX classification. The
current catalogue contains 3,775 Gen1, 7,350 Gen2 and 26 Gen3 satellites.

The three GLBs are clean-room primitive models generated by
[`tools/starlink/build-models.mjs`](../tools/starlink/build-models.mjs) and
licensed with the project (MIT). Public references evaluated while choosing a
shape included the [Sketchfab Starlink satellite model by
Malacodart](https://sketchfab.com/3d-models/starlink-spacex-satellite-0a60f6720c5141c9a1c6d71aac108b31)
(CC Attribution) and the [FetchCFD Starlink
model](https://fetchcfd.com/view-project/2300-starlink-3d-model); neither mesh is
copied into the repository, so the project owns the shipped assets without a
third-party redistribution obligation.

- **Explorer:** selecting a `STARLINK-<number>` loads that generation's model at
  the propagated position and labels it `GenN`.
- **Eyes:** the first satellite of each generation gets a `ModelComponent`
  sample at its orbit position, while the full constellation stays a single
  instanced particle draw.
- Both renderers point the model's local **+Z** (the solar-wing normal) at the
  Sun. Eyes uses an `AlignController` with `point`/`sun`; the Explorer recomputes
  the Sun direction from Earth + satellite position every frame. This gives the
  wings single-axis solar tracking instead of a fixed orientation (the display
  bus rotates with the wings).
- Models are authored in metres and use a `35` display scale (a roughly 100-800
  km marker at Earth close-up) because real 3 m satellites are invisible at
  planetary scale. This is a visual marker, not a physical-scale claim.
- The Eyes build copies `eyes/src/models/starlink/` to
  `public/eyes/models/starlink/`, and the catalogue to
  `public/eyes/data/starlink-orbits.json`; both are reproducible with
  `npm run eyes:build` / `npm run starlink:build`.

## Occlusion and labels

Starlink points, selected orbit lines and generation models use the normal WebGL
depth buffer, so far-side geometry is hidden by Earth. Body name labels are DOM
overlays and use labelOccludedBySphere: a label is hidden when the
camera-to-label segment passes through a nearer body sphere, including its leader
and marker. This prevents satellites that are actually behind Earth from showing
their names in front.

## Limitations

- The two-body propagation is a display approximation. It ignores drag, J2,
  station-keeping and covariances; it must not be used for conjunction
  assessment or operations.
- The catalogue is a generated snapshot. Re-run `npm run starlink:build` to
  refresh it against the current manifest.
- The complete OCM files remain at the source. This repository stores only the
  compact one-state-per-satellite catalogue, not a mirror of Starlink's data.
- Starlink and SpaceX are trademarks of their respective owners. The data is
  used here for public visualization with source attribution.

  closed orbit rings, invalid-state rejection and that the committed catalogue
  covers the whole manifest with finite states.

  TypeScript and production paths.
